# 9.14 — фикс «Could not find the input entity» в wipe-операции

## Симптом

Запуск `POST /accounts/{id}/dialogs/wipe` для аккаунтов 3, 5, 6, 7
возвращал HTTP 200, но в `failed[]` лежали записи вида
`ValueError: Could not find the input entity for PeerUser(user_id=...)`.
UI показывал красный тост «Wipe закончился с ошибками», хотя по факту
локальные данные удалялись корректно — просто на стороне Telegram такие
peer'ы либо уже не существовали, либо у Telethon в сессионном кэше не
было их access_hash.

## Что сделано

Разделили «реальные ошибки» и «entity уже нет в Telegram». Второе теперь
не считается ошибкой и не пугает оператора.

### Файлы

- `modules/worker/wrapper.py` — новый метод
  `prime_entity_cache_and_list() -> set[int]`. Идёт по `iter_dialogs()`
  (это side-effect-но прогревает Telethon-кэш access_hash'ей для всех
  видимых peer'ов) и возвращает множество tg_user_id, которые СЕЙЧАС
  в dialog list аккаунта.
- `modules/history/wipe.py` — переписан loop:
  1. В начале — `prime_entity_cache_and_list()` (best-effort, если упало —
     продолжаем без фильтра).
  2. Для каждого диалога:
     - если `tg_user_id` в свежем срезе → tg-side delete + local;
     - если нет → tg пропускаем, делаем только local. Категория
       `deleted_local_only`, не `failed`.
  3. Если tg-side всё-таки упал с `ValueError("Could not find the input
     entity")` (наш срез был неполный по гонке) — ловим, тоже
     считаем `deleted_local_only` через новый `_EntityNotFound`.
- `modules/ui_web/src/lib/api.ts` — ответ теперь содержит три счётчика:
  `deleted_full`, `deleted_local_only`, `deleted` (сумма, для
  обратной совместимости).
- `modules/ui_web/src/pages/DialogsPage.tsx` — тост дополняется
  фразой «Из них N — только локально (в Telegram их уже не было)»;
  красный показывается только при реальных `failed[]` или FloodWait.

## Почему так, а не иначе

- **`iter_dialogs()` как side-effect cache-warm.** Telethon не имеет
  отдельной публичной функции «прогрей кэш для всех peer'ов» — внутри
  он кэширует при любом `iter_dialogs()` / `get_entity()`. Самое чистое
  публичное API — один проход по диалогам, и заодно получаем срез того,
  что вообще существует на стороне Telegram.
- **Срез возвращаем как `set[int]`, а не как полные User-объекты.**
  В цикле нам нужен только membership test; полный snapshot профилей
  раздул бы память и в Web UI всё равно бы не пригодился.
- **Catching `ValueError` по подстроке текста.** Telethon бросает
  обычный `ValueError`, специфического исключения для «no input entity»
  у него нет. Подстрока `"Could not find the input entity"` стабильна
  во всех версиях, которые мы используем (см. их `_resolve_peer`).
  Альтернатива — catch-all + heuristic после — была бы хуже, потому что
  затёрла бы реально другие ValueError-ы (например, из user-кода
  `purge_dialog_locally`).
- **`prime_entity_cache_and_list` best-effort.** Если её вызов упал
  (например, краткий сетевой глюк), wipe всё равно проходит — просто
  без оптимизации «пропустить точно несуществующие». Это сохраняет
  устойчивость операции в условиях, когда Telegram нестабильно отвечает.
- **`deleted_local_only` отдельный счётчик, а не сумма в `failed`.**
  Оператор должен в одну секунду понять «всё локально чисто, в Telegram
  где можно — снесено». Запихать «entity gone» в `failed` смешивает
  семантику и заставляет UI парсить строки ошибок.

## Известные ограничения

- Если у аккаунта много архивных диалогов, которые Telethon не вернёт
  в `iter_dialogs()` (он по умолчанию не идёт в archive), они попадут
  в категорию `deleted_local_only`. Архив у нас в проекте не
  поддерживается явно — accept-as-is.
- Прогрев кэша занимает время пропорционально количеству диалогов
  аккаунта на стороне Telegram. Для аккаунтов с 1000+ peer'ов это
  заметные секунды. Не критично для разовой операции, но если в будущем
  понадобится частый bulk — стоит кэшировать срез между вызовами.
