# 9.25 — `dialogs.birthday` расщеплён на `birthday_day/month/year`

## Что это

Готовим колонку под расширенный профиль из 9.24/9.26/9.27. Сейчас
`dialogs.birthday` — `DATE`. Это не подходит:

- Telegram отдаёт день рождения как `{day, month, year?}` — год
  опционален. Многие пользователи указывают только день и месяц.
- `DATE` требует год; чтобы хранить «14 мая, года не знаем», нам бы
  пришлось придумывать sentinel-год (1900, 2000…) и потом везде
  отличать его от реального. Это грязный хак.

Расщепляем колонку на три `SMALLINT NULL` поля: `birthday_day`,
`birthday_month`, `birthday_year`. День+месяц всегда заполнены вместе,
год — опционально.

## Файлы

- `alembic/versions/0011_dialogs_birthday_parts.py`:
  - `DROP COLUMN birthday` (раньше всегда был NULL, данных нет → ничего
    не теряем).
  - `ADD COLUMN birthday_day SMALLINT, birthday_month SMALLINT,
    birthday_year SMALLINT` — все nullable.
  - CHECK `dialogs_birthday_chk`: либо `day` и `month` оба NULL, либо
    оба заданы в диапазоне 1–31/1–12, год — либо NULL, либо
    1900–2100. Полу-задание (только день без месяца, и т.п.) запрещено
    на уровне БД, не надеемся на чистоплотность appside-кода.
- `modules/history/routes.py`:
  - В `_dialog_to_dict` `"birthday": _iso(row["birthday"])` заменено
    на три плоских поля `birthday_day/birthday_month/birthday_year`.
    Поле раньше всегда было `null` (колонка не заполнялась), так что
    реальных клиентов не ломаем.
- `docs/database_schema.md` — табличка `dialogs` обновлена.

## Почему так, а не иначе

- **Три SMALLINT вместо JSON `birthday JSONB`.** В таблице уже всё
  плоско (`first_name TEXT`, `phone TEXT` и т.д.), JSON будет
  чужеродным. Плюс CHECK-констрейнтами три INT-поля валидируются
  тривиально, JSON-схема в Postgres — гораздо больнее.
- **Год не обязателен.** Telegram реально возвращает Birthday без
  года; писать «фиктивный 1900» и потом в UI его прятать — путь
  к ошибкам. Лучше честный NULL.
- **CHECK на парность.** Без него можно случайно положить
  `(day=14, month=NULL)` и сломать форматирование в плейсхолдере.
  Защищаем инвариант на уровне схемы.
- **DROP COLUMN в одной транзакции с ADD COLUMN.** Колонка пустая,
  никаких данных не теряем, отдельный шаг копирования не нужен.
