# 9.15 — динамические статусы диалогов (бэк + миграция)

## Что сделано

Превратили операторские «пузыри» статусов из захардкоженного списка
из 4 значений в управляемую сущность с собственной таблицей, CRUD-API
и публикацией событий. UI в этом коммите ещё пользуется старыми
4 ключами через временный адаптер — следующие коммиты введут страницу
настроек и динамический рендер `DialogListItem`.

## Файлы

Бэкенд / БД:
- `alembic/versions/0009_dialog_statuses.py` — новая таблица
  `dialog_statuses` (id, label, color hex, sort_order, timestamps,
  CHECK на формат цвета и длину лейбла), сиды 4 текущих статусов
  (`Общаемся #22c55e`, `Ждём ответ #eab308`, `Готово #94a3b8`,
  `Провал #ef4444`), `ALTER TABLE dialogs ADD COLUMN status_id`
  с FK ON DELETE SET NULL и индексом, перенос значений из
  `user_status` по CASE, `DROP COLUMN user_status`.
- `modules/dialog_statuses/__init__.py` + `service.py` + `routes.py` —
  новый модуль, полностью автономный:
  - `service.list_statuses / create_status / update_status /
    delete_status / get_status` — каталог.
  - `service.set_dialog_status(dialog_id, status_id, *, source)` —
    единственная точка входа на присвоение. Зовут и UI (через ручку),
    и будущая автоматизация (listener событий → set_dialog_status
    с `source="event:autochat.finished_by_llm"` и т.п.).
  - Routes: `GET/POST/PATCH/DELETE /dialog-statuses` + переехавшая
    из history `PATCH /dialogs/{id}/status` с новым контрактом
    body — `{status_id: int | null}` вместо `{status: string | null}`.
- `core/events.py` — два новых типа:
  - `dialog.status_changed` (per-assignment, поле `source` в data для
    аудита «кто проставил»);
  - `dialog_statuses.catalog_changed` (агрегатный, action ∈
    `created/updated/deleted`).
  - Новый модуль шины `dialog_statuses`.
- `modules/history/routes.py` — `_dialog_to_dict` теперь сериализует
  `status: {id, label, color} | null` через подцепленные `status_label`
  / `status_color` (SELECT'ы списка диалогов и одиночного диалога
  получили `LEFT JOIN dialog_statuses`). Старая ручка
  `PATCH /dialogs/{id}/status` удалена (переехала в новый модуль).
- `api/main.py` — регистрация нового роутера.

UI (временный мостик):
- `modules/ui_web/src/lib/api.ts` — `adaptDialog` теперь читает
  `d.status: {id, label, color}` и мапит 4 сидированных id обратно
  в старые ключи (`talking/waiting/done/failed`) для существующего
  `DialogSummary.user_status`. `setDialogStatus` пересылает PATCH в
  новом формате `{status_id}`. Адаптер чисто переходный — уйдёт
  вместе с рефакторингом `DialogListItem` на полный каталог.

## Почему так, а не иначе

- **Отдельный модуль `dialog_statuses/`**, а не «дописать в history»:
  каталог — автономная сущность с собственным CUD, а функция
  `set_dialog_status` — общий entry-point для UI и будущей
  автоматизации. Не должны жить рядом с поиском сообщений и нагоном
  истории.
- **`ON DELETE SET NULL` для FK** — удалить пузырь не должно сносить
  диалоги. Операторская пометка просто снимается.
- **Hex как text + CHECK regex.** Решение оператора — какой именно
  оттенок. На бэке валидируем формат, на UI добавим нативный пикер +
  поле ввода. Палитру не делаем — у оператора может быть много
  категорий, 9 готовых цветов не хватит.
- **Поле `source` в `dialog.status_changed`.** Простой задел под
  автоматизацию: одному коду слушать ту же шину, для разных триггеров
  (manual UI / listener событий) — разные значения `source`.
- **Адаптер в `api.ts`** временно мостит UI к новому бэк-контракту
  без рефакторинга компонента. Это позволило сделать коммит атомарным
  («бэк работает, UI не сломан») — следующие два коммита спокойно
  переделают визуал и удалят адаптер.

## Что НЕ сделано в этом наборе юнитов

- Автоматическое выставление статуса от событий шины. Архитектура
  готова (вся работа — снаружи позвать `service.set_dialog_status`),
  но отдельный listener-модуль будет писаться позже отдельной задачей.
- Реалтайм-инвалидация UI на `dialog_statuses.catalog_changed` через
  SSE. На старте обойдёмся `react-query.refetch()` после mutate;
  SSE подключим, когда станет тесно (например, если двое операторов
  одновременно редактируют каталог).
