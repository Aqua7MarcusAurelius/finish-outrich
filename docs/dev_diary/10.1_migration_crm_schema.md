## Изменения в схеме

**`dialogs`:**
- `gender TEXT` ('female' | 'male' | NULL) + check-constraint
- `from_crm BOOLEAN NOT NULL DEFAULT FALSE` + partial-index по `from_crm = TRUE`
- `partner_crm_terminal_reason TEXT` (одно из 'ready_for_transfer' / 'invalid' / 'no_response') + check

**`accounts`:**
- `lead_source TEXT NOT NULL DEFAULT 'manual'` (manual | partner_crm)
- `target_gender TEXT NOT NULL DEFAULT 'any'` (any | female | male)

**`dialog_statuses`:**
- новое поле `partner_terminal_status TEXT` (NULL = промежуточный, иначе —
  код для CRM при финализации)
- сиды переписаны: было 4 (Общаемся/Ждём ответ/Готово/Провал),
  стало 6: Невалид → invalid, Первый контакт, Общение, Обрыв,
  Завершен успешно → ready_for_transfer, Завершен провал → no_response.

**Новая таблица `crm_lead_pool`** (собственность модуля `partner_crm`):
`username UNIQUE`, `gender`, `fetched_at`. Индекс `(gender, fetched_at)`
для быстрого подбора воркером.

**Новая таблица `lead_evaluations`** (собственность модуля `lead_evaluator`):
`dialog_id UNIQUE FK CASCADE`, `verdict ('success' | 'archive')`,
`extracted_name/age/city/workplace/interests`, `raw_response`,
`evaluator_model`, `parse_succeeded`, таймстемпы.

**Новые ключи в `settings`** (7 штук):
- `partner_crm.poll_interval_sec=60`
- `partner_crm.pool_low_threshold=10`
- `partner_crm.refill_batch_size=50`
- `lead_evaluator.silence_check_interval_sec=300`
- `lead_evaluator.silence_to_obryv_hours=4`
- `lead_evaluator.silence_to_close_hours=48`
- `lead_evaluator.parse_retries=1`

## Почему так, а не иначе

**Сиды dialog_statuses переписываем только если каталог пустой ИЛИ совпадает
с дефолтом из 0009.** Иначе оператор уже что-то накастомил руками — DELETE
без раздумий уронил бы его работу. Лог-инвариант: после миграции в проде,
где оператор уже редактировал статусы, останется его набор без новых трёх
терминальных пузырей — придётся вручную добавить через UI. Это сознательный
компромисс между автоматизмом и безопасностью.

**`crm_lead_pool` и `lead_evaluations` в новых таблицах, а не в jsonb на
`dialogs`.** Принцип проекта — каждая таблица принадлежит одному модулю.
Поэтому: `dialogs` остаётся у `history`, новые сущности рядом.

**`username` UNIQUE на `crm_lead_pool`.** Если CRM по какой-то причине
вернёт лида повторно (race / ошибка на их стороне) — INSERT упадёт по
unique, что нормально: уже есть, ничего страшного.

**`UNIQUE(dialog_id)` на `lead_evaluations`.** Одна актуальная оценка на
диалог. Переоценка через UPSERT, истории не плодим (история ответов LLM
для аудита и так есть в `raw_response`).

**Часть про откат (`downgrade`)** написана с тем же бережным подходом:
если в новых сидах что-то поменяли — таблицу не трогаем, чтобы не
снести данные оператора.

## Проверка

```bash
docker compose exec app alembic upgrade head
docker compose exec postgres psql -U tgframework -d tgframework -c "\d dialogs"
docker compose exec postgres psql -U tgframework -d tgframework -c "\d accounts"
docker compose exec postgres psql -U tgframework -d tgframework -c "SELECT id, label, partner_terminal_status FROM dialog_statuses ORDER BY sort_order;"
docker compose exec postgres psql -U tgframework -d tgframework -c "SELECT key, value FROM settings WHERE key LIKE 'partner_crm%' OR key LIKE 'lead_evaluator%' ORDER BY key;"
```

Все 6 пузырей с маппингом, 3 новые колонки на `dialogs`, 2 на `accounts`,
обе новые таблицы созданы, 7 ключей в settings.
