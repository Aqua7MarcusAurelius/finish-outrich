# 10.2 — partner_crm: скелет модуля и HTTP-клиент

**Дата:** 2026-05-17
**Этап:** 10.2

## Что сделано

Завели новый модуль `modules/partner_crm/` — единственная точка общения
приложения с партнёрской CRM. В этом юните положили **фундамент**:
httpx-клиент, синхронные сервис-методы, четыре эндпоинта для UI.
Фоновых задач ещё нет — это юнит 10.3 (poller).

## Файлы

- `modules/partner_crm/__init__.py`
- `modules/partner_crm/errors.py` — `PartnerCrmError` → `NotConfigured` / `CrmHttpError` / `InvalidStatus`
- `modules/partner_crm/client.py` — async httpx-обёртка над `/api/l1/*`
- `modules/partner_crm/service.py` — `PartnerCrmService` (pool_size, list_pool, refill_pool, claim_lead_for_account, push_lead_started, push_lead_finalized, get_preferences)
- `modules/partner_crm/routes.py` — эндпоинты `/partner-crm/*`
- `core/config.py` — добавили `CRM_BASE_URL`, `CRM_API_TOKEN`, `OPENROUTER_MODEL_EVALUATOR`
- `core/events.py` — `Module.PARTNER_CRM` / `Module.LEAD_EVALUATOR` + 9 новых типов событий
- `api/main.py` — регистрация `partner_crm_service` в lifespan и роутера

## Эндпоинты

| Метод | Путь | Что |
|---|---|---|
| GET | `/partner-crm/health` | `{configured: bool, pool_size: int}` — лёгкая проверка для UI-бэйджа |
| GET | `/partner-crm/preferences` | Прозрачный прокси `GET /api/l1/preferences` (gender_filter, geo_filter, max_concurrent_leads, ...) |
| GET | `/partner-crm/pool` | Состояние локального пула (массив `{id, username, gender, fetched_at}`) |
| POST | `/partner-crm/pool/refill` | Body `{count}` — вручную дозалить пул из CRM (UI-кнопка "Забрать N сейчас"). Авто-дозалив придёт в 10.3. |

## События на шине

Новый модуль публикует:

| Тип | Когда |
|---|---|
| `partner_crm.pool_refilled` | Удачный refill — `{requested, fetched, inserted, skipped_duplicates}` |
| `partner_crm.refill_failed` | Сеть/4xx/5xx на /request-new |
| `partner_crm.lead_taken` | Воркер забрал лида из пула под себя |
| `partner_crm.lead_started` | `/leads/:u/start` прошёл — задел под 10.5 |
| `partner_crm.lead_start_failed` | то же, но ошибка |
| `partner_crm.status_pushed` | `/leads/:u/status` финал ушёл — задел под 10.8 |
| `partner_crm.status_push_failed` | то же, но ошибка |

`lead_evaluator.*` события зарегистрированы в `EventType`, но публиковать
их некому до юнита 10.6.

## Почему так, а не иначе

**`PartnerCrmClient` — отдельный класс, не функции.** Httpx-клиент держим
один на всё приложение для keep-alive. В `lifespan` создаём один `PartnerCrmService`,
сервис владеет клиентом и закрывает его в shutdown.

**`claim_lead_for_account` сразу с `FOR UPDATE SKIP LOCKED`.** Несколько
воркеров могут тикать почти одновременно — без skip-locked получили бы
блокировку или дублирование. SKIP LOCKED → каждый воркер получит свою
строку или None.

**`refill_pool` использует `ON CONFLICT DO NOTHING` на `username`.**
Если CRM по какой-то причине отдаст того же лида второй раз (race / баг
на их стороне) — INSERT не упадёт, просто пропустим. Возвращаем счётчик
`skipped_duplicates` чтобы это было видно в UI / логе.

**Сервис не стартует фоновых тасков в 10.2.** Сначала фундамент,
потом poller. Это разделение даёт нам "горящую" проверку: подняли модуль —
эндпоинты работают, refill можно дёрнуть руками, ничего не крутится в
фоне без надзора.

## Проверка

```bash
curl http://localhost:8000/partner-crm/health
# {"configured": true, "pool_size": 0}

curl http://localhost:8000/partner-crm/preferences
# {"ready_to_receive": true, "max_concurrent_leads": 100, "gender_filter": "female", ...}

curl http://localhost:8000/partner-crm/pool
# {"items": [], "count": 0}
```

`POST /partner-crm/pool/refill` пока не дёргаем — следующий юнит
поднимет автоматический сторож, и тогда уже будем смотреть как пул
наполняется без ручного вмешательства.

## Открытые вопросы

- В ответе CRM поле `assigned` ожидаемое (так в доке), но в обновлённой
  версии может быть `leads`. В коде проверяем оба ключа (`payload.get("assigned") or payload.get("leads") or []`).
  Если CRM пришлёт что-то третье — refill пройдёт без вставок, увидим
  в `partner_crm.pool_refilled` с `inserted=0`.
