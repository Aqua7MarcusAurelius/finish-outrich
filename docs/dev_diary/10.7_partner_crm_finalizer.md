# 10.7 — partner_crm: финал-листенер (push в CRM при терминальном пузыре)

**Дата:** 2026-05-17
**Этап:** 10.7

## Что сделано

Закрыли последний кусок партнёрского контура: при появлении
терминального пузыря на CRM-диалоге автоматически уходит финальный
`POST /api/l1/leads/:username/status` в партнёрскую CRM.

Это второе (и последнее) касание CRM на лида — первое было
`POST /leads/:u/start` из юнита 10.4. Между ними CRM ничего о
статусе не слышит (наши промежуточные пузыри живут только локально).

## Файлы

- `modules/partner_crm/finalizer.py` — новый `PartnerCrmFinalizer`
- `api/main.py` — регистрация в lifespan, рядом с poller'ом

## Логика срабатывания

```
event dialog.status_changed
        │ tip: dialog_id, status_id
        ▼
SELECT d.from_crm, d.partner_crm_terminal_reason,
       d.username, ds.partner_terminal_status
FROM dialogs d JOIN dialog_statuses ds ON ds.id = d.status_id
        │
        ▼
1. from_crm = FALSE                              → skip
2. partner_terminal_status IS NULL (промежуточный) → skip
3. terminal_status_to_push = stored_reason || partner_terminal_status
4. POST /api/l1/leads/{username}/status {status: terminal_status_to_push}
5. UPDATE dialogs.partner_crm_terminal_reason = NULL
        │
        ▼
publish partner_crm.status_pushed или .status_push_failed
```

## Почему так, а не иначе

**Источник правды для terminal_status — `dialogs.partner_crm_terminal_reason`,
а не `dialog_statuses.partner_terminal_status`.** Это важно для
случая когда оценщик закрыл лида:

- Оценщик ставит `Завершен провал` → у пузыря `partner_terminal_status = 'no_response'`.
- Оценщик пишет `dialogs.partner_crm_terminal_reason = 'no_response'`.

Эти два значения совпадают по дизайну. Но если позже партнёр CRM
добавит отдельный код `archive` — мы поменяем маппинг в `lead_evaluator`
(где принимается решение), а пузырь и его partner_terminal_status
останутся теми же. Источник правды — там где принимается решение.

**Сначала смотрим stored_reason, потом fallback на пузырь.** Если
оператор сам нажал пузырь (без оценщика и без silence_watcher) —
`stored_reason=NULL`, тогда берём prefix у самого пузыря. Это безопасно:
все три терминальных пузыря в каталоге имеют корректный
`partner_terminal_status`.

**Очистка `stored_reason = NULL` после push'а.** Защита от повторного
push'а если оператор переключит обратно и снова на терминал.

**Шапка через consumer group "partner-crm-finalizer".** Отдельная
от других — позволяет независимо ack'ать события. Если упадёт
конкретный push, перепрочитанные события можно будет переиграть
через стандартный механизм `record_failure` (как у других модулей).

**Push НЕ блокирует acknowledge события.** Если CRM недоступна —
ловим `PartnerCrmError`, пишем warning, ack-аем событие как
обработанное. Иначе при долгом сбое CRM consumer-group зависнет
на одной и той же группе событий. Лучше реакция "залогировано в шину
как partner_crm.status_push_failed, оператор увидит и решит вручную".

## Полная картина двух касаний CRM

```
[Лид принят в crm_lead_pool]
   ↓ worker_auto_runner claim
[autochat.create_session]
   ↓ успех                                 ← 10.4 (10.4)
[partner_crm_service.push_lead_started]
   POST /api/l1/leads/:u/start             ← касание №1: in_progress
   ↓
[Переписка идёт; статусы локально меняются:
 Первый контакт → Общение → (Обрыв?) — CRM это не видит]
   ↓
[Терминальный пузырь поставлен оценщиком/таймером/оператором]
   ↓ event dialog.status_changed
[PartnerCrmFinalizer]                       ← 10.7 (этот юнит)
   POST /api/l1/leads/:u/status             ← касание №2: terminal
                                              (ready_for_transfer | invalid | no_response)
```

## Проверка

Контейнер `app` стартует чисто, в логе появилась строка
`PartnerCrmFinalizer loop started` (на DEBUG-уровне — INFO мы
оставили только для активного push).

End-to-end проверка пойдёт когда:
1. Воркер с `lead_source='partner_crm'` завершит диалог;
2. Оценщик закроет диалог в `Завершен успешно`;
3. Finalizer должен опубликовать `partner_crm.status_pushed` с
   `status='ready_for_transfer'` и `username=...`.

Лог события можно увидеть на странице "События" в UI или
`SELECT * FROM events_archive WHERE type LIKE 'partner_crm.%' ORDER BY time DESC LIMIT 10`.

## Открытые вопросы

- Двусторонняя синхронизация (если партнёр сменит статус на их
  стороне) пока не делаем. Когда добавим — это будет ещё один
  poller-style таск в partner_crm.
