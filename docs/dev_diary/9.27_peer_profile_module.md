# 9.27 — модуль `peer_profile` — consumer цепочки расширенного профиля

## Что это

Четвёртый коммит из 5. Новый модуль `modules/peer_profile/`, который
замыкает цепочку:

```
worker → message.received → history → INSERT dialogs
                                    → publish dialog.created
                                          │
                                          ▼
                              peer_profile (этот коммит)
                                    → wrapper.fetch_full_profile
                                    → publish dialog.profile.fetched
                                          │
                                          ▼
                              history (9.26) → UPDATE dialogs.bio,
                                               birthday_*
```

После этого коммита фича работает end-to-end: первое сообщение от
нового собеседника → bio и день рождения подтянулись в БД → `partner_bio`
в промптах начинает реально подставляться (плейсхолдер уже был).
Плейсхолдер `{partner_birthday}` — следующий коммит (9.28).

## Файлы

- `modules/peer_profile/__init__.py` — пустой маркер пакета (по
  конвенции с другими модулями).
- `modules/peer_profile/service.py` — `PeerProfileService`:
  - consumer-group `peer-profile-fetcher` поверх Redis Stream;
  - `_handle` пропускает только `dialog.created`, остальное молча
    ack'ает (как у `history.service`, `transcription.service`);
  - `_on_dialog_created` — фильтрует обязательные поля payload'а
    (`account_id`, `dialog_id`, `telegram_user_id`); если воркер
    для аккаунта offline (`get_wrapper(...)` → `None`) — info-лог
    и skip без публикации;
  - вызов `wrapper.fetch_full_profile(telegram_user_id)`:
    - `SessionExpired` — info-лог + return; враппер уже опубликовал
      `account.session_expired`, не дублируем;
    - `WrapperError` / прочие — warning + return; bio не критичен,
      зависать в ретраях не имеет смысла;
  - публикует `dialog.profile.fetched {dialog_id, telegram_user_id,
    bio, birthday}` с `parent_id` = id исходного `dialog.created`
    (цепочка трассируется в Event Log).
- `api/main.py`:
  - импорт `PeerProfileService`;
  - сервис создаётся в lifespan ПОСЛЕ AutoChat (нужен `get_wrapper`
    из `worker_manager`);
  - shutdown: гасим до `worker_manager`, чтобы consumer не словил
    свежевыдранный `wrapper.client = None` посреди fetch'а.

## Соответствие принципам

- **Модуль не знает о соседях напрямую.** Один callable
  `get_wrapper(account_id)` — больше ничего. Все остальные общения
  через шину.
- **Любое общение с Telegram — через враппер.** Метод
  `wrapper.fetch_full_profile`, никаких прямых клиентов.
- **В чужие таблицы не лезем.** UPDATE `dialogs` — делает только
  `history`, мы ему просто шлём событие.
- **Падение fetch'а не валит очередь.** Каждое событие — свой
  try/except; poison-message защита уже встроена в `bus.read_group` /
  `record_failure`.
- **Имя в прошедшем времени.** `dialog.profile.fetched`.

## Почему именно так, а не иначе

- **Отдельный модуль вместо метода в worker'е.** Хотя метод можно
  было приклеить прямо к worker'у (он уже общается с Telegram),
  тогда worker стал бы реагировать ещё и на события шины — это
  смешение ролей. Текущий worker слушает только NewMessage handler
  Telethon, всё остальное вне Telegram прокидывается через события.
  Не хочется ломать инвариант ради экономии файла.
- **Skip при offline-воркере, не retry.** При offline бывает только
  если воркер успел упасть между `history.INSERT` и нашим чтением
  события — редкость. Гонять retry-петли в Redis (DLQ-таймауты,
  backoff, и т.д.) ради этой редкости — лишняя сложность.
  Если станет проблемой — добавим `dialog.profile.refetch.requested`
  с UI-кнопкой; пока эта потребность не доказана.
- **`get_wrapper` через callable, не импорт `WorkerManager`.**
  Тот же паттерн, что у AutoChatService и WorkerAutoRunnerService.
  Облегчает тесты и не вяжет в граф зависимостей.

## Что НЕ сделано

- Плейсхолдер `{partner_birthday}` в autochat — коммит 9.28.
  `{partner_bio}` уже работает: history записал в `dialogs.bio`,
  autochat читает в [generation.py:185](modules/autochat/generation.py#L185).
- UI-индикация «профиль дотянут / не дотянут» в карточке диалога —
  скорее всего не нужно. Если bio пусто — оно просто не отрендерится.
  Если оператор захочет ручную дотяжку — добавим тогда.
