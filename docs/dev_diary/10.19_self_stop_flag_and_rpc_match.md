# 10.19 — Фиксы поверх 10.16/10.17: self-stop работает, Premium/Payment лиды → invalid

**Дата:** 2026-05-22
**Этап:** 10.19 (баг-фикс, отчёт с прода)

Bug-report: `docs/Fix/transient_self_stop_and_privacy_misclassification.md`.

## Что чинили

Два бага поверх 10.16/10.17:

1. **Self-stop через `asyncio.create_task(self.stop(...))` не срабатывал**
   — воркер оставался `is_running=true`, событие
   `auto_runner.stopped reason=transient_error:*` не публиковалось.
2. **`PRIVACY_PREMIUM_REQUIRED` и `ALLOW_PAYMENT_REQUIRED`** уезжали
   через generic `except Exception` в `SendFailedTransient` → бесконечно
   реинзертились в пул. Партнёрский CRM не получал `invalid`.

## Фикс #1 — флаг вместо `create_task`

`asyncio.create_task(self.stop(...))` имел race-condition с самим
loop-task'ом и с возможным конкурентным start(). В проде stop_task
завершался тихо, last_status не обновлялся, событие не публиковалось.

Новая схема:

- В `WorkerAutoRunnerService.__init__`: `self._self_stop_requested: dict[int, str]`
  (account_id → reason).
- В `_try_start_dialog` при категории Б ставим
  `self._self_stop_requested[account_id] = f"transient_error:{err_code}"`,
  логируем `log.info("self-stop requested ...")`.
- В `_account_loop` сразу после `_try_start_dialog` проверяем флаг —
  если стоит, зовём `_do_self_stop(account_id, reason)` и `return`.
  Loop-task завершается естественно, без cancel-машинерии.

Новый `_do_self_stop`:
- Снимает себя из `_tasks` (без `_lock` — мы внутри своего task'а).
- `_set_running(account_id, False, last_status=f"stopped ({reason})")`
  внутри try/except + log.exception.
- `bus.publish(AUTO_RUNNER_STOPPED, data={reason})` тоже в try/except.
- Логирует `start` и `done` для диагностики.

Race с публичным `start()` / `stop()` исключён — флаг проверяется
в одном месте (внутри loop'а), DB-update идёт линейно, никакого
cancel() параллельно.

## Фикс #2 — `RPCError` с текстовым матчем

В нашей версии telethon отсутствуют классы `PrivacyPremiumRequiredError`
и `AllowPaymentRequiredError` — они приходят как generic
`telethon.errors.RPCError` со словами в `.message`. Поэтому в
`autochat/service.py` после блока специфичных классов добавлен ещё один:

```python
_RPC_CANNOT_WRITE_MARKERS: tuple[str, ...] = (
    "PRIVACY_PREMIUM_REQUIRED",
    "ALLOW_PAYMENT_REQUIRED",
    "USER_BANNED_IN_CHANNEL",
    "CHAT_RESTRICTED",
)

except RPCError as e:
    msg = str(e)
    if any(m in msg for m in _RPC_CANNOT_WRITE_MARKERS):
        raise CannotWrite(...) from e
    raise SendFailedTransient(...) from e
```

Catch-блок `except RPCError` стоит **перед** generic `except Exception`,
поэтому RPCError больше не утекает в дефолтный транзиент.

## Verify

Docker сейчас прилёг локально — live-проверки нет. Code review:

1. **Self-stop**: флаг ставится в `_try_start_dialog`, проверяется в
   `_account_loop` ОДИН раз за итерацию, на той же task'е. Никаких race.
   `_do_self_stop` идёт линейно, ловит исключения отдельно для каждой
   операции — даже если bus.publish упадёт, `_set_running(False)`
   успеет.
2. **RPCError matching**: catch-цепочка теперь:
   `WrapperSessionExpired → FloodWaitError → _TELETHON_CANNOT_WRITE_ERRORS
   → RPCError(text-match) → Exception`. Любая `PRIVACY_PREMIUM_REQUIRED`
   попадёт в RPCError-блок и через маркер уйдёт в `CannotWrite`.

После того как docker встанет, прогнать:

```sql
-- Должно быть >0 событий с self-stop reason после спровоцированного транзиента
SELECT type, data->>'reason' FROM events_archive
WHERE type='auto_runner.stopped'
  AND data->>'reason' LIKE 'transient_error:%'
  AND time > NOW() - INTERVAL '10 minutes';

-- Премиум/payment лиды должны идти как CANNOT_WRITE, не SEND_FAILED_TRANSIENT
SELECT data->>'error_code' AS code, COUNT(*)
FROM events_archive
WHERE type='auto_runner.lead_skipped'
  AND time > NOW() - INTERVAL '1 hour'
  AND (data->>'error' ILIKE '%PRIVACY_PREMIUM_REQUIRED%'
       OR data->>'error' ILIKE '%ALLOW_PAYMENT_REQUIRED%')
GROUP BY 1;
-- Ожидается: CANNOT_WRITE > 0, SEND_FAILED_TRANSIENT = 0
```

Из bug-report'а — те ~4 лида которые сейчас бумерангом возвращаются
в пул из-за неправильной классификации. SQL для их поиска:

```sql
SELECT DISTINCT data->>'username' AS username
FROM events_archive
WHERE type = 'auto_runner.lead_skipped'
  AND data->>'error_code' IN ('SEND_FAILED_TRANSIENT','SESSION_EXPIRED')
  AND (data->>'error' ILIKE '%PRIVACY_PREMIUM_REQUIRED%'
       OR data->>'error' ILIKE '%ALLOW_PAYMENT_REQUIRED%'
       OR data->>'error' ILIKE '%USER_BANNED_IN_CHANNEL%');
```

Эти `username`'ы можно:
1. Удалить из `crm_lead_pool` (если они там) — чтобы перестали
   повторно подбираться.
2. Закрыть в CRM как `invalid` через ручной `POST /api/l1/leads/:u/status`
   или через service-вызов `partner_crm.push_lead_finalized(...,
   terminal_status="invalid")`.

Отдельной кнопки в UI не делал — частный сценарий, проще руками SQL+API.
Если станет регулярной задачей — оформим как «спасательный» эндпоинт.

## Открытые вопросы

- В bug-report'е был случай где лид `@alin148bambola` с реальным
  `ALLOW_PAYMENT_REQUIRED` получил error_code `SESSION_EXPIRED`. Не
  смог воспроизвести по коду — `_guard` ловит только `_SESSION_EXPIRED_ERRORS`,
  которые жёстко session-killers (`AuthKeyError`,
  `UserDeactivatedError`, и т.п.), не RPCError 406. Возможно тот воркер
  параллельно потерял сессию и совпало. После 10.19 этот лид всё равно
  пойдёт через `CannotWrite` (новый RPCError-блок отработает раньше
  чем generic), даже если параллельно есть session-issue.
- Bump telethon до версии где есть `PrivacyPremiumRequiredError` /
  `AllowPaymentRequiredError` — позволил бы заменить text-matching на
  isinstance(). Сейчас text-match достаточно надёжен, bump откладываем
  до случая когда понадобится из-за чего-то ещё.
