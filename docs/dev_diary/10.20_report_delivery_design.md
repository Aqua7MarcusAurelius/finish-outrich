# 10.20 — report_delivery: дизайн доставки success-отчётов в TG-группы

**Дата:** 2026-06-09
**Этап:** 10.20

## Что сделано

Зафиксировали дизайн новой надстройки `report_delivery`: когда HTML-отчёт
по диалогу попадает в папку `success/`, он автоматически заливается
сервисным Telegram-аккаунтом в группу выгрузки соответствующего воркера.
Раньше оператор забирал файлы из MinIO вручную.

Сам код — в следующих юнитах (10.21+). Здесь — только решения и их причины.

## Картина потока

```
[диалог закрыт терминальным пузырём]
        │ event dialog.status_changed
        ▼
ReportConsumer (10.8)  → save_report_for_dialog
        │ кладёт HTML в MinIO: success|failed|archive/{worker}_@{user}_{ts}.html
        │ publish autochat.report_saved {account_id, minio_key, folder}
        ▼
ReportDeliveryService (10.22)               ← НОВОЕ
        │ folder == "success"?  нет → ack, выходим
        │ worker = префикс из minio_key (до "_@")
        │ chat_id = REPORT_GROUP_MAP[worker];  нет → ack + log
        │ дедуп: SETNX report_delivered:{dialog_id} в Redis
        │ data = minio.get_object(minio_key, REPORTS_BUCKET)
        ▼
service-аккаунт.send_file(chat_id, data, caption=…)
        │ publish report.delivered | report.delivery_failed
```

## Почему так, а не иначе

**Триггер — `autochat.report_saved`, а не отдельный поллинг MinIO.**
Шина уже публикует «отчёт сохранён» с `folder` и `minio_key` (10.8).
Реагируем на событие — никакого периодического обхода бакета. Это и есть
«финальная точка», о которой просил заказчик: к моменту события файл
гарантированно лежит в MinIO.

**Фильтр `folder == "success"`.** Заливаем только удачные диалоги. Папку
определяет оценщик ещё в 10.8 (`_determine_folder`), нам её отдают готовой
в событии — не дублируем логику вердикта.

**Группу узнаём из имени файла, а не из БД.** Ключ MinIO начинается с кода
воркера (`SAD_03_RU_@user_…html`). Кода достаточно, чтобы по карте
`REPORT_GROUP_MAP` найти `chat_id`. Так не трогаем схему `accounts` и не
заводим миграцию — соответствие воркер→группа живёт в конфиге.

**Карта групп — JSON в `.env` (`REPORT_GROUP_MAP`).** Группы статичны,
оператор сам знает их `chat_id` и добавляет туда сервис-аккаунт участником.
Числовой `chat_id` — единственный надёжный идентификатор для приватных
групп без `@username`. Если в будущем понадобится правка на лету без
рестарта — переложим в таблицу `settings` (там и живут tunable-настройки).

**Отдельный сервисный аккаунт, а не отправка «каждый воркер сам в свою
группу».** Один админский аккаунт состоит во всех группах и шлёт все
отчёты. Минус зависимости: лид-воркер диалога может быть уже остановлен к
моменту доставки — сервис-аккаунт живёт независимо и всегда на связи.
Задел «для администрирования» — этот же аккаунт переиспользуем под будущие
служебные задачи.

**Сервис-аккаунт держит СВОЁ подключение в модуле `report_delivery`, а не
запускается как лид-воркер через `WorkerManager`.** Воркер (`Worker`)
подписывается на входящие, гонит нагон истории — админскому аккаунту это не
нужно. Модуль поднимает голый `TelegramWrapper`, делает `connect()` +
прогрев entity-кэша (один `get_dialogs`, чтобы `send_file(chat_id)`
резолвился) и всё. Двойного коннекта на одну сессию не будет, потому что
лид-воркером его не стартуем.

**«Заглушка» — фильтр в `WorkerManager.list_workers()`.** И `GET /workers`,
и `GET /accounts` читают эту одну функцию — отфильтровав там аккаунт с
именем `SERVICE_ACCOUNT_NAME`, скрываем его из UI разом. В SSE он тоже не
всплывёт: статуса в Redis у него нет (как воркер не стартует). Плюс guard в
`start()` — на случай прямого вызова API.

**Дедуп через Redis (`SETNX`), без таблицы.** `dialog.status_changed` может
прийти не раз — флаг `report_delivered:{dialog_id}` гарантирует одну
отправку на диалог. Redis уже в стеке, миграция не нужна. Флаг ставим
только после успешной отправки; при сбое — снимаем, чтобы `record_failure`
смог переиграть.

**Best-effort, как у соседних консьюмеров.** Нет группы в карте / сервис-
аккаунт офлайн — логируем, публикуем `report.delivery_failed`, ack-аем
событие (через стандартный `record_failure`/force-ack), чтобы consumer-group
не завис на одном событии. Доставка отчёта не должна ронять основной поток.

## Открытые вопросы

- **Повторная отправка при success→другой статус→success.** Пока шлём один
  раз на диалог (дедуп по `dialog_id`). Если понадобится переотправлять при
  каждом повторном входе в success — снимать флаг на смене статуса.
- **Подпись к файлу.** По умолчанию подробная (воркер, @партнёр, вердикт,
  поля оценщика, время). Состав полей легко поменять в `_build_caption`.
- **Несколько групп на воркера / одна группа на несколько воркеров.** Карта
  1→1 (воркер→chat_id). Если потребуется веер — значение сделаем списком.
