# 10.17 — Гранулярная классификация ошибок отправки (FloodWait != CannotWrite)

**Дата:** 2026-05-22
**Этап:** 10.17 (баг-фикс, прод-отчёт)

## Что было сломано

Bug-report: `docs/Fix/cannot_write_overclassifies_floodwait.md`.

10.16 правильно разделил поведение в `worker_auto_runner` по двум
категориям ошибок — A (лид невалидный → CRM invalid) и Б (транзиент →
reinsert + stop). Но `autochat/service.py` имел catch-all
`except Exception → CannotWrite`, который сваливал в код `CANNOT_WRITE`
буквально всё что падало на `wrapper.send_message`, включая
**`FloodWaitError`** — наш троттлинг от Telegram.

В результате: воркер ловит FloodWait → autochat бросает `CannotWrite` →
`worker_auto_runner` видит код `CANNOT_WRITE` (категория A) → пушит в
партнёрский CRM `lead_status=invalid` → лид теряется для нас (партнёр
закрывает у себя). Серия FloodWait'ов = серия ложных `invalid`.

## Что сделал

### 1. Новые классы ошибок в `autochat/errors.py`

- `FloodWait(seconds=N)` — TG троттлинг. Код `FLOOD_WAIT`. Транзиент.
- `SendFailedTransient` — любая прочая транзиентная сетевая/RPC ошибка.
  Код `SEND_FAILED_TRANSIENT`. **Безопасный дефолт** для «непонятного»:
  лучше задержать на воркере, чем ошибочно закрыть лида у партнёра.
- `CannotWrite` остался, но теперь жёстко означает «лид физически
  недоступен» (privacy / block / Premium-only).

### 2. Разбор ошибок `send_message` в `autochat/service.py`

Импорт конкретных классов из `telethon.errors.rpcerrorlist`:
- `FloodWaitError` → `FloodWait`
- `ChatWriteForbiddenError`, `PremiumAccountRequiredError`,
  `UserBlockedError`, `UserIsBlockedError`, `UserNotMutualContactError`,
  `UserPrivacyRestrictedError`, `YouBlockedUserError` → `CannotWrite`
- `WrapperSessionExpired` → `AutoSessionExpired` (как было)
- всё остальное → `SendFailedTransient`

Тут же выкинули catch-all `except Exception → CannotWrite`.

### 3. Классификатор в `worker_auto_runner._CRM_INVALID_ERROR_CODES`

Не трогали — там уже только три истинно-invalid кода:
`USERNAME_NOT_FOUND`, `USERNAME_UNAVAILABLE`, `CANNOT_WRITE`.
Новые `FLOOD_WAIT` / `SEND_FAILED_TRANSIENT` не попадают в этот set →
автоматически идут по категории B (reinsert в пул + self-stop).

### Заметка про недоступные классы

Bug-report упоминал `PrivacyPremiumRequiredError` и
`AllowPaymentRequiredError` из telethon.errors.rpcerrorlist — в нашей
версии telethon их нет. Семантический эквивалент `PremiumAccountRequiredError`
(который есть) — добавил его в `_TELETHON_CANNOT_WRITE_ERRORS`.
`AllowPaymentRequiredError` (платный приём DM через Stars) — не критично
для MVP, попадёт через `SendFailedTransient` → лид вернётся в пул, на
другом воркере проверится. Если этот сценарий начнёт всплывать часто —
выясним точное имя класса в актуальной telethon и добавим явно.

## Файлы

- `modules/autochat/errors.py` — `FloodWait`, `SendFailedTransient`;
  переписан docstring `CannotWrite`.
- `modules/autochat/service.py` — telethon-импорты + `_TELETHON_CANNOT_WRITE_ERRORS`
  + новый except-chain в send_message.
- `docs/Fix/cannot_write_overclassifies_floodwait.md` — пометил FIXED.

## Verify

Smoke-проверка кодов:
```
$ docker compose exec app python -c "..."
CannotWrite.code: CANNOT_WRITE
FloodWait.code: FLOOD_WAIT status: 429
SendFailedTransient.code: SEND_FAILED_TRANSIENT
Invalid codes (Category A): ['CANNOT_WRITE', 'USERNAME_NOT_FOUND', 'USERNAME_UNAVAILABLE']
FLOOD_WAIT в invalid? False
SEND_FAILED_TRANSIENT в invalid? False
```

End-to-end:
1. Воркер с активным FloodWait → следующий `auto_runner.lead_skipped`
   с `error_code=FLOOD_WAIT` (не `CANNOT_WRITE`).
2. В events_archive **нет** соответствующего `partner_crm.status_pushed status=invalid`.
3. В `crm_lead_pool` username вернулся.
4. Воркер → `auto_runner.stopped reason=transient_error:FLOOD_WAIT`.
5. На «нормальном» воркере без FloodWait тот же лид при следующем тике
   успешно стартует → `auto_runner.lead_sent`.
6. Лид с реально privacy / blocked → `CANNOT_WRITE` → CRM `invalid`,
   как и должно быть.

## Расхлёбывание ранее потерянных лидов

В bug-report есть SQL для нахождения ложно-`invalid`-нных лидов (когда
`data.error_code='CANNOT_WRITE'` И `data.error ILIKE '%Too many requests%'`).
Отдельный «спасательный» эндпоинт не делал — bug-report показывает
SQL прямо для оператора. Если станет регулярной задачей — оформим как
кнопку в UI.

## Открытые вопросы

- **Платные DM (Stars)** — `AllowPaymentRequiredError` не в той версии
  telethon что у нас. Пока попадёт через дефолт `SendFailedTransient`
  (безопасный — лид в пул вернётся). Если станет частым кейсом — найдём
  актуальное имя класса и добавим в invalid-список явно.
- **Метрика «сколько раз reinsert на этот username»** — сейчас нет
  ограничителя. Лид с системной проблемой может крутиться бесконечно.
  В 10.16 уже отметили как future-work, здесь только усугубляется
  (раньше после FloodWait лид сгорал как invalid, теперь — крутится).
