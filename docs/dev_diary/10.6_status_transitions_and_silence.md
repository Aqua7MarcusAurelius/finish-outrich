# 10.6 — Авто-транзиции статусов + таймеры тишины

**Дата:** 2026-05-17
**Этап:** 10.6

## Что сделано

Закрыли логику движения диалога по операторским пузырям без участия
оператора:

1. **Event-driven** (внутри `LeadEvaluatorService._on_message_saved`):
   - первое исходящее на диалог без статуса → "Первый контакт";
   - первое входящее на диалог без статуса → "Общение";
   - входящее на "Первый контакт" → "Общение" (лид ответил);
   - входящее на "Обрыв" → "Общение" (лид вернулся).

2. **Timer-driven** (`SilenceWatcher`):
   - "Общение" + последнее **входящее** старше 4ч → "Обрыв";
   - "Первый контакт" / "Обрыв" + любое сообщение старше 48ч →
     "Завершен провал" + `partner_crm_terminal_reason='no_response'`.

## Файлы

- `modules/lead_evaluator/silence_watcher.py` — `SilenceWatcher` (новый файл)
- `modules/lead_evaluator/service.py` — extended:
  - `_handle` теперь ветвится по типу события
  - `_on_message_saved` — auto-транзиции по факту сохранения
  - `_status_id` — ленивый кэш ID пузырей по лейблу
  - `_label_cache` в `__init__`
- `api/main.py` — `SilenceWatcher` подключён рядом с `LeadEvaluatorService`

## Поток (как меняются пузыри без участия оператора)

```
[autochat отправил первое сообщение CRM-лиду]
     │ MESSAGE_SAVED is_outgoing=true, dialog.status_id=NULL
     ▼
LeadEvaluatorService._on_message_saved
     → set_dialog_status("Первый контакт")
     → publish dialog.status_changed

[Лид ответил через час]
     │ MESSAGE_SAVED is_outgoing=false, dialog.status_id=Первый контакт
     ▼
LeadEvaluatorService._on_message_saved
     → set_dialog_status("Общение")

[Лид замолчал на 5 часов]
     ▼ SilenceWatcher tick
LeadEvaluatorService SilenceWatcher
     → "Общение" + last_in > 4h → set_dialog_status("Обрыв")

[Лид так и не вернулся, прошло 2 дня]
     ▼ SilenceWatcher tick
SilenceWatcher
     → UPDATE dialogs.partner_crm_terminal_reason='no_response'
     → set_dialog_status("Завершен провал")
     → publish dialog.status_changed   ← partner_crm в 10.8 это услышит
```

## Почему так, а не иначе

**Event-driven и timer-driven разделены физически.** Event-driven —
часть `LeadEvaluatorService` consumer-loop'а (там и так шумит MESSAGE_SAVED).
Timer-driven — отдельная фоновая таска (`SilenceWatcher`), независима,
не блокирует consumer.

**Кэш `_label_cache` живёт в памяти процесса навсегда (без TTL).**
MESSAGE_SAVED — очень частое событие. Делать SELECT по `dialog_statuses`
на каждый MSG было бы излишне. Если оператор переименует пузырь —
старое имя в кэше промахнётся, новое подтянется при следующем обращении.
Размер кэша ограничен числом меток (≤6 в текущем сетапе).

**Условие транзиции "Общение → Обрыв" — по последнему ВХОДЯЩЕМУ, а не
по любому сообщению.** Если мы каждые 30 минут пишем "ну как там?",
а лид молчит — это всё ещё обрыв. Поэтому JOIN с `messages` фильтрует
по `is_outgoing=false`.

**Условие "Первый контакт/Обрыв → Завершен провал" — по любому
сообщению.** В этих статусах "тишина" означает "нет новых событий"
вообще, а не "лид не пишет". Если мы шлём в Первый контакт пинги
без ответа — оно тоже считается отсчётом 48ч.

**Reason пишется ДО смены статуса.** В одной транзакции SQL:
сначала UPDATE `partner_crm_terminal_reason`, потом set_dialog_status
(который публикует событие). Так partner_crm в 10.8 увидит
согласованное состояние (reason + новый status_id).

**Терминальные пузыри (Завершен успешно / Завершен провал / Невалид)
event-driven обработчик не трогает.** В матче нет условия "что было".
Если терминал уже выставлен — никакое входящее сообщение не вернёт
диалог в Общение. Защита от регресса.

## Проверка

Сервис запустился, в логе:
- `LeadEvaluatorService loop started`
- `SilenceWatcher loop started`

End-to-end проверка пройдёт когда:
1. Воркер CRM начнёт диалог → должен появиться "Первый контакт".
2. Лид ответит → "Общение".
3. Через 4ч тишины (или подкрутить настройку до 60с для теста) → "Обрыв".
4. Ещё через 48ч → "Завершен провал" с `no_response`.

## Открытые вопросы

- Сценарий "лид написал нам ПЕРВЫМ" (без autochat) — попадёт в
  ветку "first incoming → Общение". Это нормально для холодных
  входящих, но если для них хочется отдельного статуса (например
  "Холодный входящий") — заведём в 10.10 через UI.
- `silence_check_interval_sec=300` (5 мин). При больших объёмах диалогов
  и низком интервале часы тишины могут "пропустить" границу на минуту
  — это допустимо, в пределах одного цикла.
