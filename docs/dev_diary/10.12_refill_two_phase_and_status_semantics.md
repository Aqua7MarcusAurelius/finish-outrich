# 10.12 — Двухфазный рефилл + правильная семантика статуса CRM

**Дата:** 2026-05-19
**Этап:** 10.12 (post-MVP коррекция)

## Что сделано

Переработали логику взятия лида в наш `crm_lead_pool` под уточнения от
оператора и реальные коды партнёрской CRM.

**Раньше (10.4):**
- Воркер забирает лида из пула → autochat начал → `POST /leads/:u/start`
  пушит «взяли в работу» в CRM.
- В пул кладём только то что приходит через `/request-new`.

**Теперь (10.12):**
- Рефилл двухфазный:
  1. `GET /api/l1/leads?status=new` — все назначенные нам лиды, чьё
     `lead_status=new` (мы их ещё не двигали).
  2. Если в пуле всё ещё < target → `POST /request-new` на остаток.
- В обоих фазах при взятии лида в локальный пул **сразу** зовём
  `POST /api/l1/leads/:u/status {"status":"in_progress"}` — лид
  на стороне CRM становится `lead_status=in_progress`.
- Из `worker_auto_runner._try_start_dialog` убран отложенный пуш
  «start» — теперь это делается на этапе пула.

## Что мы узнали о CRM пока подключали

**`/start` нам не подходит.** Возвращает `409 l1_account_not_assigned` —
endpoint требует чтобы на нашей CRM-сессии был привязан TG-аккаунт
через `/api/l1/set-primary-account`. Это для L1-операторов которые
работают через CRM-овский Telethon. У нас свой Telethon, нет смысла
дублировать.

**`/status` работает без привязки.** Меняет `lead_status` напрямую,
независимо от того есть ли у нас l1_account. Это и есть наш канал
управления лидом — и для in_progress, и для финальных значений.

**В CRM у лида ДВА поля статуса:**
- `status` — workflow-уровень assignment (`new` / `taken` /
  `in_progress` / финалы). Управляется CRM-ом, мы его не трогаем.
- `lead_status` — наша прогрессия (`new` / `in_progress` / финалы).
  Меняем через `POST /status`.

**Фильтр `?status=` в `/leads` смотрит на оба поля.** То есть
`?status=new` вернёт всё что либо `status=new`, либо `lead_status=new`.
Для нашей цели "ещё не в работе у нас" подходит фильтр `status=new` —
он точно вернёт лидов с `lead_status=new` (которые мы ещё не
трогали).

## Что важно знать оператору

**Параметр `count` в `/pool/refill {count: N}` контролирует только
вторую фазу.** Первая фаза забирает ВСЁ что назначено и в `lead_status=new`.
Поэтому если попросить refill на 3 — а CRM уже назначила 100 — придёт
все 100 + ещё 3 запрошенных = 103. Это правильное поведение: мы не
хотим оставлять «назначенных, но не в работе» в подвешенном
состоянии у партнёра.

**Если CRM упала и `/status in_progress` не сработал на конкретном
лиде** — он не попадёт в наш пул. Событие `partner_crm.lead_start_failed`
в `/events`. На следующем тике сторожа попробуем снова (лид всё ещё
в `lead_status=new` на их стороне).

**Уже назначенные при первом запуске** (которые лежали в пуле без
обновления статуса) — на следующем тике автоматически получат
`/status in_progress`, в локальный пул вставка пропускается через
ON CONFLICT.

## Проверка

```bash
curl -X POST http://localhost:8000/partner-crm/pool/refill \
  -H "Content-Type: application/json" -d '{"count":3}' | jq
# {
#   "requested": 3,
#   "from_assigned": 106,
#   "from_request_new": 0,
#   "inserted": 105,
#   "skipped_duplicates": 1,
#   "start_failed": 0
# }
```

106 свежих лидов из пула CRM пришли все за раз. Все они теперь
`lead_status=in_progress` в CRM. 1 пропущен (`ignatenko_aa` уже была
в пуле — её просто перепинали в `in_progress` без дубля).
