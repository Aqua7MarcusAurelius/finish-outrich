# 10.4 — Подбор лидов из пула + проброс gender/from_crm в диалог

**Дата:** 2026-05-17
**Этап:** 10.4

## Что сделано

Свели цепочку "пул CRM → воркер → autochat → диалог" end-to-end.
Теперь воркер с `accounts.lead_source='partner_crm'` на тике берёт
лидов из общего `crm_lead_pool` (с фильтром по gender), стартует
автодиалог через autochat, а metadata из CRM (`gender`, `from_crm`)
доезжает до колонки `dialogs` при первом создании ряда. После успешного
старта в партнёрскую CRM улетает `POST /leads/:username/start` —
"взяли в работу".

## Файлы

- `modules/worker_auto_runner/service.py`:
  - конструктор получает `partner_crm_service` (опциональный, для обратной совместимости)
  - новый хелпер `_get_account_lead_meta(account_id) → (lead_source, target_gender)`
  - `_account_loop` выбирает источник: `manual` → своя очередь, `partner_crm` → пул через `partner_crm_service.claim_lead_for_account`
  - `_try_start_dialog` получает `gender` и `from_crm`, передаёт в autochat, после успеха — пушит "in_progress" в CRM
- `modules/autochat/service.py`:
  - `create_session` принимает `gender: str | None = None` и `from_crm: bool = False`
  - при публикации `message.received` для первого сообщения кладёт `data.partner_crm_meta = {gender, from_crm}` если есть что класть
- `modules/history/service.py`:
  - `_on_message_received` достаёт `partner_crm_meta` из data и пробрасывает в `_upsert_dialog`
  - `_upsert_dialog` теперь записывает `gender` и `from_crm` в `dialogs` при ПЕРВОМ INSERT (на UPDATE поля не трогаются)
- `api/main.py`: `WorkerAutoRunnerService` получает `partner_crm_service`

## Flow одного CRM-лида

```
[crm_lead_pool, заполнен poller'ом]
        │
        │ воркер тикнул, lead_source=partner_crm
        ▼
PartnerCrmService.claim_lead_for_account()
   • SELECT FOR UPDATE SKIP LOCKED + DELETE из пула
   • publish partner_crm.lead_taken
        │
        ▼  worker_auto_runner → autochat.create_session(username, gender, from_crm=True)
AutoChatService.create_session()
   • resolve, send first message
   • publish wrapper.message.received с data.partner_crm_meta={gender, from_crm: True}
        │
        ▼ history loop
HistoryService._on_message_received → _upsert_dialog
   • INSERT dialogs (..., gender, from_crm)
   • publish dialog.created
        │
        ▼ worker_auto_runner._try_start_dialog (после возврата create_session)
PartnerCrmService.push_lead_started()
   • POST /api/l1/leads/:username/start    → CRM ставит in_progress
   • publish partner_crm.lead_started
```

## Почему так, а не иначе

**Метаданные через `message.received.data.partner_crm_meta`, а не отдельным
событием или Redis-кэшем.** История уже владеет `dialogs`, она же
обрабатывает первое сообщение — значит ей и удобно записать поля
при INSERT'е. Альтернативы (Redis-кэш с TTL / отдельная партнёрская
таблица / отдельный consumer на `dialog.created`) добавили бы либо
fragility (кэш), либо лишнюю сущность, либо нарушение "один писатель
на таблицу". Этот вариант минимален: одно поле в payload, два
дополнительных параметра в `INSERT`.

**`from_crm` и `gender` пишутся только на INSERT, не на UPDATE.** Если
оператор когда-то общался с этим юзером вручную, а потом по совпадению
тот же `@username` пришёл из CRM — мы не задним числом не меняем
статус диалога. Это сознательное решение: история диалога имеет
большую инерцию чем источник лида.

**`_get_account_lead_meta` — отдельный SELECT, а не кэш.** На каждый
тик одного воркера — один запрос. С учётом `interval_sec >= 60` это
копеечно, зато оператор может крутить `lead_source` без перезапуска.

**`push_lead_started` — не фатально если упало.** Лид уже у нас в
работе локально (autochat пишет, история записана). Если CRM
недоступна — событие `partner_crm.lead_start_failed` появится в шине,
оператор увидит. Можно будет пересинхронизировать вручную или
автоматом потом (вне scope этого юнита).

**`autochat.create_session` принимает gender/from_crm как опциональные
keyword-only.** Старые вызовы (через `POST /autochat/start` из UI)
работают без изменений — там передаётся только username.

## Проверка

Контейнер `app` поднялся без ошибок.

Тест записи через `_upsert_dialog` с `partner_crm_meta`:
```bash
docker compose exec -T app python -c "..."
# dialog_id=618 was_inserted=True
# {'id': 618, 'username': 'crm_test_user', 'gender': 'female', 'from_crm': True}
```

Endpoint `/partner-crm/health` отвечает `pool_size=0` — пул всё ещё
пустой потому что не включён ни один CRM-воркер. End-to-end
проверка с реальным забором из CRM пойдёт уже на работающем UI
(когда оператор переключит конкретный аккаунт на `lead_source='partner_crm'`).

## Открытые вопросы

- `accounts.lead_source` сейчас меняется только через SQL — UI-селект
  идёт в 10.10. До того лиду из CRM некуда придти, кроме как через
  ручной апдейт `UPDATE accounts SET lead_source='partner_crm'`.
