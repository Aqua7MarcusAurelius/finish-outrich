# 10.22 — report_delivery: сервис доставки + регистрация в lifespan

**Дата:** 2026-06-09
**Этап:** 10.22

## Что сделано

Сам модуль доставки: `ReportDeliveryService` — bus-consumer на
`autochat.report_saved`, который при `folder == "success"` сервисным
аккаунтом заливает HTML из MinIO в группу выгрузки воркера. Подключён в
lifespan рядом с `ReportConsumer`.

## Файлы

- `modules/report_delivery/__init__.py` — пустой пакет.
- `modules/report_delivery/service.py` — `ReportDeliveryService`:
  - своё TG-подключение сервис-аккаунта (`_connect`, прогрев entity-кэша);
  - consumer-loop (`run`) с переподключением;
  - `_handle` — фильтр success → воркер → группа → дедуп → отправка;
  - `_build_caption` — подробная подпись (воркер, собеседник, поля
    оценщика, время);
  - события `report.delivered | report.delivery_failed | report.delivery_skipped`.
- `api/main.py` — импорт, старт таска в lifespan, остановка в shutdown
  (рядом с `report_consumer`).

## Поток внутри `_handle`

```
event autochat.report_saved
   │ type==report_saved? data.folder=="success"?         нет → ack, выходим
   │ dialog_id / minio_key / account_id есть?             нет → warn, ack
   │ worker = accounts.name по account_id
   │ chat_id = REPORT_GROUP_MAP[worker]                   нет → SKIPPED, ack
   │ SETNX report_delivered:{dialog_id}                   занят → ack (уже слали)
   ▼
   blob = minio.get_object(minio_key, REPORTS_BUCKET)
   caption = _build_caption(dialog_id, worker)
   wrapper.send_file(chat_id, blob, filename, caption)
   ▼
   publish report.delivered            (ошибка → снять claim + report.delivery_failed)
```

## Почему так, а не иначе

**Воркер берём по `account_id` из события, а не парсим префикс файла.**
В `autochat.report_saved` уже лежит `account_id` — один `SELECT name`
надёжнее, чем резать имя файла по `_` (в коде воркера `SAD_03_RU` сами есть
подчёркивания, граница `{worker}_{partner}` неоднозначна). Группу всё равно
«видно по файлу» в смысле «по воркеру, который его произвёл» — просто
определяем воркера детерминированно. Имя файла используем как имя вложения.

**Своё подключение, а не `WorkerManager.get_wrapper`.** Сервис-аккаунт не
лид-воркер: ему не нужны подписки на входящие и нагон истории. Поднимаем
голый `TelegramWrapper`, `connect()` + один `get_dialogs` для прогрева
entity-кэша (иначе `send_file(chat_id)` не зарезолвит приватную группу,
т.к. StringSession не помнит access_hash между рестартами). Зависимости от
запущенности лид-воркеров — ноль.

**Группа создаётся с `start_id="$"`.** Доставка — исходящий сайд-эффект. На
первом деплое не хотим, чтобы консьюмер прочитал ~10k старых событий из
хвоста Redis Stream и вывалил в группы кучу старых отчётов. `"$"` = только
новые success после включения фичи.

**Дедуп — `SETNX` claim ДО отправки, снятие при ошибке.** Занимаем
`report_delivered:{dialog_id}` перед `send_file`; на любом сбое снимаем —
чтобы доставку можно было повторить (повторным событием/вручную). На
успехе флаг живёт 90 дней (повторный `dialog.status_changed` не сошлёт
файл дважды). Claim ставим уже ПОСЛЕ проверки на наличие группы — иначе
добавленная позже группа осталась бы заблокированной флагом.

**Известные сбои отправки → `ack` + `report.delivery_failed`, без вечного
pending.** Консьюмеры здесь читают только `>` (новые), pending не
перечитывается. Поэтому не оставляем сбойное событие висеть: публикуем
`report.delivery_failed` (оператор видит в ленте), ack-аем. Файл остаётся в
MinIO — переотправку при необходимости добавим отдельным эндпоинтом.
`SessionExpired` обрабатываем особо: роняем подключение, `run()` переподнимет.

**Пустая карта / нет сервис-аккаунта → молча выключаемся.** Без
`REPORT_GROUP_MAP` или без авторизованного `service`-аккаунта `run()`
логирует причину и выходит. Фича опциональна, приложение поднимается как
обычно.

## Проверка

- `python -m py_compile` модуля и `api/main.py` — OK.
- Полный импорт-прогон локально невозможен (Docker-зависимости: telethon,
  asyncpg, minio). Живой прогон — в КТ5 (10.24): поднять `app`, проверить в
  логе `ReportDelivery loop started` и довести один CRM-диалог до
  `Завершен успешно`.

## Открытые вопросы

- Ручная переотправка сбойной доставки (эндпоинт `POST
  /report-delivery/dialogs/{id}/resend`) — если на практике сбои частые.
- Бэк-офф переподключения сейчас фиксированный (30с) — при долгом
  session_expired сервис-аккаунта это повторяет `account.session_expired`
  в ленте раз в 30с. Если будет мешать — увеличить шаг.
