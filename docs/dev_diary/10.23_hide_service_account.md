# 10.23 — report_delivery: «заглушка» — сервис-аккаунт скрыт из UI

**Дата:** 2026-06-09
**Этап:** 10.23

## Что сделано

Сервис-аккаунт доставки (имя `SERVICE_ACCOUNT_NAME`, по умолчанию `service`)
больше не светится в UI и не запускается как лид-воркер.

## Файлы

- `modules/worker_manager/service.py`:
  - `import settings` из `core.config`.
  - `list_workers()` — `... FROM accounts WHERE name <> $1 ...` со
    `SERVICE_ACCOUNT_NAME`. Скрывает аккаунт сразу из `GET /workers` и
    `GET /accounts` (оба читают эту функцию).
  - `start()` — guard: если имя строки == `SERVICE_ACCOUNT_NAME`, бросаем
    новый `ServiceAccountNotStartable` (409).
  - новый класс ошибки `ServiceAccountNotStartable(ManagerError)`.

## Почему так, а не иначе

**Фильтр в `list_workers()` — единственный чокпоинт.** И страница
«Воркеры» (`GET /workers`), и список аккаунтов на «Диалогах»
(`GET /accounts` → `manager.list_workers()`) читают эту одну функцию.
Отфильтровали по имени там — скрыли везде, без правок UI и без миграции.
В SSE `/workers/stream` аккаунт тоже не всплывёт: статуса в Redis у него
нет, потому что воркером он не стартует.

**Скрываем по имени, а не по новому флагу/колонке.** Колонка `is_service`
потребовала бы миграцию — а заказчик просил «не врезать ничего, заглушку».
Имя берём из того же `SERVICE_ACCOUNT_NAME`, что и модуль доставки, —
один источник правды.

**Guard в `start()` — защита от прямого вызова API.** Из UI кнопки «старт»
у скрытого аккаунта нет, но `POST /workers/{id}/start` через curl сработал
бы и поднял второй коннект на ту же сессию (модуль доставки уже держит
свой). Пара строк `409 SERVICE_ACCOUNT_NOT_STARTABLE` закрывают дыру.
`reconcile_on_boot` сервис-аккаунт не трогает: у него нет worker-статуса.

## Открытые вопросы

- Авторизация сервис-аккаунта идёт обычным мастером «новый аккаунт»; на
  момент создания он на миг появится в списке, пока ему не присвоено имя
  `service`. Это разовая операция настройки, отдельного флоу не делаем.
