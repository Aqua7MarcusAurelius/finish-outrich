# 9.26 — history публикует `dialog.created` и записывает `dialog.profile.fetched`

## Что это

Третий коммит из 5 в фиче «дотянуть расширенный профиль один раз
при появлении нового диалога». Учит модуль истории:

1. На каждой первой вставке `dialogs` (а не на обновлении) публиковать
   `dialog.created` — это сигнал для `peer_profile` сходить за bio
   и днём рождения. Подписаться может кто угодно (UI, CRM-export
   и т.д.) — не закрепляем за peer_profile эксклюзивно.
2. Получать обратное событие `dialog.profile.fetched` от `peer_profile`
   и записывать bio/birthday_* в `dialogs`.

Замыкает цепочку коммит 9.27, где появляется сам модуль
`peer_profile`. До его прихода `dialog.created` уйдёт в архив без
подписчиков — это нормально, dead-letter не активируется.

## Файлы

- `modules/history/service.py`:
  - Топ-докстринг обновлён: появилась новая строка в маршрутизации
    событий (`dialog.profile.fetched`).
  - `_handle` маршрутизирует новый тип на `_on_dialog_profile_fetched`.
  - `_upsert_dialog`:
    - Сигнатура: `-> int` → `-> tuple[int, bool]`. Второй элемент —
      `was_inserted`.
    - `RETURNING id, (xmax = 0) AS was_inserted`. У свежевставленной
      строки `xmax = 0`, у обновлённой `xmax = id транзакции,
      апдейтнувшей её` — отсюда надёжный признак ветки.
  - `_on_message_received`:
    - Распаковывает `(dialog_id, dialog_was_inserted)`.
    - После публикации `message.saved`, если `dialog_was_inserted` —
      публикует `dialog.created {dialog_id, telegram_user_id}` с
      `parent_id` = id исходного `message.received`. Срабатывает
      ровно один раз за жизнь диалога.
  - Новый метод `_on_dialog_profile_fetched`:
    - Читает `dialog_id`, `bio`, `birthday: {day, month, year} | null`.
    - `UPDATE ... SET bio = COALESCE($2, bio), birthday_day = COALESCE(...)`
      и т.д. — повторная дотяжка не сотрёт ручную правку оператора.
    - Битый payload (без `dialog_id`) — warning + skip, без падения.

## Соответствие принципам

- **История — единственный writer dialogs.** UPDATE из нового
  хендлера остался внутри неё. Никто другой эту таблицу не трогает.
- **Шина — основной канал.** Цепочка `INSERT → dialog.created →
  peer_profile → dialog.profile.fetched → UPDATE` идёт через события.
  Прямых вызовов между модулями нет.
- **Имена в прошедшем времени.** `dialog.created`,
  `dialog.profile.fetched` — соответствуют конвенции.
- **COALESCE при UPDATE.** Тот же паттерн, что в `_upsert_dialog` —
  ручные правки/более свежие данные не перетираются NULL'ом.

## Почему `xmax = 0`, а не другой признак

Альтернативы:
- `RETURNING created_at, updated_at` и сравнение их на appside —
  раса с другими апдейтерами и зависимость от точности NOW().
- Отдельный SELECT перед INSERT — лишний роунд-трип, плюс гонка
  с другим воркером того же account_id (даже если её сейчас нет,
  закладывать дыру не хочется).
- Постгрес-системный `xmax` — атомарно, нативно, ровно одно поле
  в RETURNING. Известная идиома, есть в документации Postgres.

## Что НЕ сделано

- Модуль `peer_profile`, который слушает `dialog.created` и публикует
  `dialog.profile.fetched`. Коммит 9.27.
- Плейсхолдер `{partner_birthday}` в autochat — коммит 9.28
  (`{partner_bio}` уже работает; как только `peer_profile` начнёт
  заполнять колонку, он перестанет быть пустым автоматически).
