# 10.3 — partner_crm: фоновый сторож пула

**Дата:** 2026-05-17
**Этап:** 10.3

## Что сделано

Добавили фоновую задачу `PartnerCrmPoller`, которая раз в N секунд
смотрит размер `crm_lead_pool` и автоматически дозаливает его из CRM
если пул просел ниже порога. Подключили в lifespan между сервисом
`partner_crm` и автозапуском воркеров.

## Файлы

- `modules/partner_crm/poller.py` — `PartnerCrmPoller`, `_has_active_crm_worker()`, `_get_int_setting()`
- `api/main.py` — создание/таска/останов poller'а в lifespan

## Логика тика

```
каждые partner_crm.poll_interval_sec секунд:
    если модуль не сконфигурирован           → пропускаем
    если pool_size >= pool_low_threshold     → пропускаем
    если нет ни одного активного CRM-воркера → пропускаем
    иначе                                    → service.refill_pool(refill_batch_size)
```

"Активный CRM-воркер" — это аккаунт с `lead_source='partner_crm'`,
`is_active=TRUE` и его `worker_auto_runners.is_running=TRUE`.

Все три параметра (`poll_interval_sec`, `pool_low_threshold`,
`refill_batch_size`) читаются из таблицы `settings` каждый тик —
оператор крутит без рестарта.

## Почему так, а не иначе

**Не качаем "впрок" если нет потребителей.** Партнёрская CRM имеет
лимит `max_concurrent_leads` — если у нас никто не работает, а мы
качаем — занимаем чужой квоту впустую. Проверка `_has_active_crm_worker`
исключает этот случай.

**Тик через `wait_for(stop_event.wait(), timeout=interval)` вместо
`asyncio.sleep`.** Так таска просыпается мгновенно при shutdown,
а не ждёт до конца интервала.

**Ошибки тика не валят таску.** `except Exception` + `log.exception`
— чтобы временный сбой (БД дёрнулась / CRM временно недоступна) не
выводил сторож из строя на всё время до рестарта.

**Логирование на INFO для "refill triggered", DEBUG для скипов.** Иначе
при пустом пуле и одном воркере без partner_crm мы бы получили лог-спам
каждые 60 секунд.

## Проверка

Poller подключился без ошибок:
```bash
docker compose exec app python -c \
  "from modules.partner_crm.poller import PartnerCrmPoller; print('OK')"
# OK
```

Все 8 текущих аккаунтов `lead_source='manual'`, ни один runner не
включён → poller тикнет, увидит "некому пилить", вернётся в сон.
Никаких событий `partner_crm.pool_refilled` не должно возникать —
это и есть штатное поведение пока CRM-воркеров нет.

End-to-end проверка (поднять CRM-воркер, дождаться авто-дозалива,
увидеть лидов в `crm_lead_pool`) пойдёт в 10.4, где будет где-то
взять `lead_source='partner_crm'` через UI/SQL.

## Открытые вопросы

- Текущий `_has_active_crm_worker` спрашивает БД на каждый тик. Для
  60-секундного интервала это копеечно. Если в будущем интервал
  опустится до 5-10 секунд — стоит закешировать через Redis с TTL.
