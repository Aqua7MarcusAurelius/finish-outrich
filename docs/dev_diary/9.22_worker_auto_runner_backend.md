# 9.22 — Worker Auto Runner: бэкенд

## Что это

Автомат «сам себе оператор» для конкретного воркера: оператор
вписывает список юзернеймов в очередь, нажимает Play — воркер каждые
N секунд ± jitter сам стартует с очередной строкой новый автодиалог
(тот же flow, что у ручной кнопки «+ Новый автодиалог»).

Этот коммит — только бэкенд: таблица, сервис, HTTP-ручки, события
шины, регистрация в lifespan. UI следующим коммитом.

## Файлы

- `alembic/versions/0010_worker_auto_runners.py` — таблица
  `worker_auto_runners (account_id PK FK, is_running, queue TEXT[],
  interval_sec ≥60, jitter_sec ≥0, last_action_at, last_status,
  created_at, updated_at)`. CASCADE при удалении аккаунта.
  CHECK-констрейнты на длину очереди (≤1000) и допустимые значения.
- `modules/worker_auto_runner/__init__.py` — пустой маркер пакета.
- `modules/worker_auto_runner/service.py` — `WorkerAutoRunnerService`:
  - CRUD по `worker_auto_runners` (единственный писатель в таблицу);
  - `start(account_id)` / `stop(account_id)` — поднимают/гасят
    per-account asyncio.Task; идемпотентны, без phantom-событий;
  - `_account_loop` — основной цикл: pop username, `autochat_service
    .create_session`, sleep `interval ± random(-jitter, jitter)`
    (не меньше `MIN_INTERVAL_SEC=60`), chunked sleep для быстрого
    реагирования на падение воркера;
  - `run()` — фоновый bus-consumer для `worker.stopped` /
    `worker.crashed`: гасит соответствующего runner'a;
  - `reset_on_boot()` — UPDATE WHERE is_running=true → false при
    старте приложения; runner'ы НЕ возобновляются автоматически.
- `modules/worker_auto_runner/routes.py`:
  - `GET    /workers/{id}/auto-runner` — текущая конфа + state;
  - `PATCH  /workers/{id}/auto-runner` — поля `queue`, `interval_sec`,
    `jitter_sec`. Юзернеймы санитизируются: `strip()`, убирается
    лидирующий `@`, пустые отфильтровываются.
  - `POST   /workers/{id}/auto-runner/start` (200/404/409);
  - `POST   /workers/{id}/auto-runner/stop`.
- `core/events.py`:
  - модуль `WORKER_AUTO_RUNNER = "worker_auto_runner"`;
  - типы `auto_runner.started / stopped / lead_sent / lead_skipped /
    queue_empty`. Это и есть «лог автомата» — читается на странице
    Event Log с фильтром `module=worker_auto_runner`. Отдельной
    таблицы для логов нет.
- `api/main.py`:
  - импорт и подключение `auto_runner_router`;
  - создание сервиса в lifespan ПОСЛЕ AutoChatService (зовём его
    `create_session`); вызов `reset_on_boot`; запуск `run()`;
  - shutdown — auto_runner гасится ПЕРВЫМ (чтобы перестал звать
    autochat'у, пока та ещё в shutdown'е).

## Соответствие принципам

- **Модуль не знает о соседях напрямую** — только два callable'а:
  `get_wrapper(account_id)` (чтобы понять «воркер жив?») и
  `autochat_service.create_session(...)` (стартовать диалог).
  В чужие таблицы не лезем.
- **Шина — основной лог** — все события автомата (started, stopped,
  lead_sent, lead_skipped, queue_empty) публикуются туда; отдельной
  таблицы логов нет.
- **В таблицу пишет один модуль** — `worker_auto_runners` — только мы.
- **Любое общение с Telegram — через враппер** — сами в TG не идём;
  идём через `autochat.create_session` → `wrapper.send_message`.
- **Падение одного воркера не валит других** — каждый цикл — свой
  Task с try/except.
- **WorkerManager → нам уведомления через шину**, не прямой вызов.
  `worker.stopped` и `worker.crashed` события (которые публикует
  WorkerManager сам) подхватываются нашим bus-consumer'ом и гасят
  соответствующего runner'a.

## Почему так, а не иначе

- **`is_running` сбрасывается на boot.** Зафиксировали с оператором:
  после рестарта `app` Play не возобновляется автоматически. Это
  предсказуемо после деплоя и убирает риск «после рестарта поплыло
  само».
- **Sleep делается чанками по 5 сек.** Без этого после `worker.stopped`
  ждать пришлось бы до конца `interval_sec` (например, 20 минут).
  Чанк-sleep + проверка `get_wrapper()` в каждой итерации даёт реакцию
  ≤5 сек. Bus-подписка даёт ещё быстрее, чанк-sleep — страховка на
  случай если событие потеряется.
- **`autochat.create_session` исключение → SKIPPED**, идём дальше.
  Юзернейм уже удалён из очереди — повторно не пробуем. Так оператор
  видит в Event Log что было: ровно те юзернеймы, которые не
  зарезолвились / другие ошибки.
- **Pop из очереди — атомарно через `SELECT ... FOR UPDATE`** в
  транзакции. Если параллельно прилетит PATCH с новой очередью,
  гонки за «кто что взял» не будет.
- **`MIN_INTERVAL_SEC=60`.** Защита от случайного 0/1 — оператор
  бы зафлудил TG и заработал бан.

## Что НЕ сделано в этом коммите

- UI — Play/Pause/Settings на карточке воркера; будет в 9.23.
- Авто-репорт статусов в CRM при finished_by_llm — отдельный модуль
  потом, когда подключим CRM как источник лидов.
