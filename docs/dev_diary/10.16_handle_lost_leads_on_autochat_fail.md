# 10.16 — Не теряем CRM-лидов при сбое autochat

**Дата:** 2026-05-20
**Этап:** 10.16

## Проблема

Когда воркер забирал лида из `crm_lead_pool` (`claim_lead_for_account`
делает DELETE) и потом autochat падал (FloodWait, OpenRouter недоступен,
prompt пустой, и т.п.) — лид:

- Удалён из локального пула → больше никто его не возьмёт.
- На стороне CRM `lead_status=in_progress` (был выставлен при заборе).
- Никакой переписки не начата.

Итог: лид «теряется», висит мёртвым у партнёра. Особенно болезненно при
FloodWait'ах, которые срабатывают пачкой.

## Решение

Разделили ошибки autochat на две категории и обрабатываем по-разному.

### Категория А: тех-фейл лида (он физически недоступен)

Коды:
- `USERNAME_NOT_FOUND` — @username не резолвится
- `USERNAME_UNAVAILABLE` — privacy
- `CANNOT_WRITE` — заблокировал нас / privacy сообщения

Действие:
- `partner_crm.push_lead_finalized(username, "invalid")` → CRM-статус
  становится `invalid`, лид закрыт.
- В наш пул не возвращаем.
- Воркер продолжает работу (лид невалидный, не наша проблема).

### Категория Б: транзиентная ошибка (проблема у нас)

Всё что не А — FloodWait, OpenRouter упал, `WORKER_NOT_RUNNING`,
`PROMPT_NOT_CONFIGURED`, `GENERATION_FAILED`, `SESSION_EXPIRED`, etc.

Действие:
- `partner_crm.reinsert_into_pool(username, gender)` — лид кладётся
  обратно в наш пул. CRM-статус НЕ трогаем (он уже `in_progress`).
- **Останавливаем этот воркер** через `self.stop(account_id, reason=...)`.
  Это публикует `AUTO_RUNNER_STOPPED` с reason `transient_error:<код>` —
  оператор видит в шине что у конкретного воркера проблема.
- Оператор разбирается с причиной (например ждёт пока FloodWait
  истечёт) и заново жмёт Play.
- Лид при этом остаётся в общем пуле — любой другой свободный воркер
  с подходящим target_gender его подберёт.

## Файлы

- `modules/partner_crm/service.py` — новый `reinsert_into_pool(username, gender)`:
  простой INSERT в `crm_lead_pool` с `ON CONFLICT DO NOTHING` (без /status,
  лид уже in_progress на CRM).
- `modules/worker_auto_runner/service.py`:
  - константа `_CRM_INVALID_ERROR_CODES`
  - `_try_start_dialog` теперь категоризует ошибки, дёргает либо
    `push_lead_finalized("invalid")`, либо `reinsert_into_pool` + self-stop

## Почему self-stop, а не просто продолжать

Транзиентные ошибки часто кучей. FloodWait — это знак что Telegram
сказал «погоди N секунд» для всего аккаунта. Если воркер продолжит
тикать каждые 60 сек — он будет дёргать новых лидов, FloodWait не даст
ничего отправить, лиды будут крутиться через reinsert. Бессмысленно.

Лучше: остановить, дождаться оператора (или самого FloodWait),
запустить вручную. Лид в пуле уже не теряется — это главное.

OpenRouter упал? Тоже стоп, оператор подождёт и стартанёт. То же для
пустого промта (нужно вмешательство).

## Поведение для не-CRM (ручных) лидов

Для `from_crm=False` поведение не меняется: ошибка → `LEAD_SKIPPED`,
лид (если он был в очереди) уже удалён pop'ом, и всё. Оператор сам
впишет заново если надо.

## Что осталось как было

- Успешный запуск → `LEAD_SENT`, дальше обычный flow с
  push'ом `start` (на этапе пула был) и финалом по терминальному
  пузырю.
- Сама последовательность ошибок autochat (resolve → LLM → send) не
  меняется — мы реагируем только на финальный exception.

## Проверка

Сейчас вживую проверить можно так:
1. Пул с лидами есть, воркер на `lead_source=partner_crm`.
2. Затемнить в worker'е initial-промт (поставить пустую строку)
   → следующий тик упадёт с `PROMPT_NOT_CONFIGURED`.
3. В events_archive:
   - `auto_runner.lead_skipped` с `error_code=PROMPT_NOT_CONFIGURED`
   - `auto_runner.stopped` с `reason=transient_error:PROMPT_NOT_CONFIGURED`
4. В `crm_lead_pool` тот лид снова есть.
5. Воркер в state `is_running=false` — кнопка Play.

## Открытые вопросы

- Если лид крутится через reinsert на разных воркерах и везде падает —
  пул заполнится «проклятым» лидом. На MVP принимаем, добавим `retry_count`
  если станет проблемой.
- FloodWait считается транзиентом → reinsert + stop. После того как
  FloodWait истечёт и оператор включит воркер обратно — он снова может
  получить FloodWait на следующем сообщении. Тут уже только живой
  оператор разбирается.
